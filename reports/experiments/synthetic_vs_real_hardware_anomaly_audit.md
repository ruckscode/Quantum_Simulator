# Synthetic vs real-hardware anomaly detection audit

**Audit date:** 2026-10-26  
**Disposition:** A defensible synthetic-versus-real-hardware accuracy comparison cannot be calculated from the repository evidence inspected. The repository contains no verified IBM hardware execution record with an independently established anomaly label. Hardware accuracy, balanced accuracy, macro F1, sensitivity, specificity, and false-positive rate are therefore **not available**. No synthetic or mocked result is used as a substitute.

## Scope and evidence reviewed

The audit began with the five requested artifacts and checked the related saved evidence in `reports/ibm_validation_report.json`, `reports/final_demo_report.json`, hardware phase 3.3 and phase 3.5 reports, the controlled fault-isolation reports/cases, ML data foundation and pipeline audits, and repository report/index files for execution IDs, job IDs, calibration capture provenance, labels, and metrics. No experiment was rerun, no IBM service or credentials were accessed, and no hardware job was submitted.

## Search results: hardware records, snapshots, labels, metrics

- **Saved actual IBM execution records:** none verified in the checked repository evidence. The explicit adapter result has no job ID and states no real execution. The hardware preflight record is blocked before IBM contact. A code path capable of submitting jobs is not evidence that it was used.
- **Actual IBM calibration snapshots:** none verified. The saved calibration snapshot is labeled `OFFLINE_FIXTURE`, with backend `offline-fixture`; the local readiness reports describe fixture parsing and explicitly deny live capture. Simulator hardware profiles are configured parameters, not captured calibrations.
- **Independently labeled real-hardware anomaly cases:** none found. The offline IBM report says no independent execution ground truth was supplied. The other hardware anomaly labels belong to constructed simulator scenarios or synthetic labels.
- **Real-hardware metrics:** none. The IBM report's metric fields are null. No saved confusion matrix or labelled hardware test set was identified.
- **Synthetic/simulator metrics:** available only within their own targets and designs. Finite-shot detection rates and controlled-simulator classification metrics must not be merged or relabeled as one another. Historical ML metrics are explicitly uncertified for independent generalization by the ML provenance reports.

## Can one same-target comparison be scored now?

No. There is no pair of eligible test sets with the same independently defined binary target (“anomalous” versus “normal”), the same frozen detector/model, disjoint development and test data, and comparable input/provenance. In particular, a known synthetic scenario label is not interchangeable with a label inferred from a real backend calibration snapshot, and output-distribution deviation alone does not establish a hardware fault. The synthetic finite-shot test has a null/effect-size target for distribution comparison, while diagnosis scenarios include NORMAL, PROGRAM_FAULT, HARDWARE_ANOMALY, and ambiguous outcomes. Neither supplies real-hardware labels.

Accordingly, **no synthetic-versus-hardware accuracy, balanced accuracy, macro F1, sensitivity, specificity, or false-positive rate is reported here**. This does not mean the simulator metrics do not exist; it means they do not form a valid matched comparison with device data. Distribution detection rates remain their own endpoint and are not called classification accuracy.

## Exact next step for a valid comparison

1. First acquire an **authorized, read-only live preflight** for one explicitly named IBM backend, following the Phase 3.5 blocker. This obtains backend identity/status, topology, and a timestamped calibration snapshot without submitting a job. The existing report specifically requires the backend name; no backend should be guessed.
2. Before any execution, define and freeze the binary target and labeling rules, including how ambiguous/program-fault cases are handled; select the detector/model and threshold using development data only; predeclare independent partitioning, sample-size/uncertainty method, and acceptance criteria. Keep distribution-test endpoints separate from classifier endpoints.
3. If the preflight passes, separately authorize a bounded acquisition of repeated executions with raw counts, requested/returned shots, circuit and transpiled circuit, physical/logical and classical-bit mapping, backend/job IDs, execution intervals, source/runtime hashes, and calibration snapshots linked to every run. Independently adjudicate labels from evidence separate from model predictions; preserve uncertain cases rather than forcing labels.
4. Build a synthetic test set and a real-hardware test set with the same binary target and compatible case design. Lock both test sets before scoring the same frozen detector/model. Then report confusion matrices and accuracy, balanced accuracy, macro F1, sensitivity, specificity, and false-positive rate with uncertainty intervals and per-class support. If acquisition or labels cannot meet these conditions, continue to report hardware accuracy as unavailable.

This audit itself performed no external access or hardware execution. No existing simulator, production ML model, historical result, or QML workspace was modified.
