## Scope and evidence rules

This checklist governs whether an official result from the separately authorized confirmation run may be accepted. A successful unit-test suite, `git diff --check`, a valid signature by itself, or the existence of a JSON result is insufficient to pass Gate B or Gate C. Each evidence item must identify its artifact, version/hash, collector, collection time, identity/environment, and independent verifier. Retain evidence read-only in the project’s designated audit location, with a digest manifest.

The feasibility review establishes that the current workspace does not contain a provisioned trust root, dedicated task identity/task DACL, immutable runtime bundle, durable anti-replay system, protected host-attestation key, or authenticated reviewer key. The driver currently imports dependencies before authorization (`experiments/finite_shot_null_confirmation.py:23–35`), checks on-disk hashes/module origins (`:191–235`) without binding loaded bytes atomically, consumes a marker (`:338–351`, invoked at `:482`), and writes an unsigned JSON result (`:523–543`). These are baseline observations, not accepted controls. See also `reports/experiments/finite_shot_null_confirmation_control_feasibility_review_20261016.md`, `reports/experiments/finite_shot_null_confirmation_control_implementation_plan_20261016.md`, and `reports/experiments/finite_shot_null_confirmation_execution_design_decision_20261016.md`.

## Three acceptance gates

### Gate A — Implementation readiness

**Purpose:** authorize implementation work only, not trust provisioning or experiment execution.

Accept Gate A only when the threat model, official/nonofficial result boundary, trust roles, complete worker/runtime closure, import/DLL policy, anti-replay storage and rollback model, interruption state machine, result-attestation protocol, verifier responsibilities and negative-test plan are specified with no unresolved architectural bypass. Direct legacy helper output must be explicitly nonofficial and unable to satisfy the official verifier. Each design decision must have an owner and testable acceptance criterion.

**Required evidence:** reviewed architecture/control specification, call-graph and bypass analysis, artifact closure, state-machine/sequence description, result schema and threat-based test plan; independent architecture/security review recorded. Repository unit tests may support but cannot alone pass this gate.

### Gate B — Host provisioning acceptance

**Purpose:** establish the actual Windows boundary.

Accept Gate B only when controls 1, 3, 4, 5 and the production-key portions of 6 are provisioned and verified on the intended host under actual operator/task identities. Retain administrator evidence for task DACL, identity/token, effective ACLs and denied writes, immutable bundle and actual loaded closure, durable anti-replay and restart/rollback tests, and restricted host-key use. Gate B must be reviewed by an independent Windows/security verifier. No local test, `git diff --check`, configuration flag, or assertion in a JSON file is evidence of effective OS protection.

### Gate C — Experiment authorization

**Purpose:** authorize one exact run, subject to explicit user authorization.

Accept Gate C only when Gate A and Gate B are accepted; reviewer identity and independence are externally authenticated; the signed approval matches the exact preregistration, worker/runtime manifest, execution configuration, trust-root identity, unique run ID and registered seed allocation; all resource and decision parameters match; and the user explicitly authorizes execution. Valid signature alone is insufficient: identity/key trust and all bindings must be independently checked. Gate C is run-specific and single-use; it expires on any relevant artifact/configuration change or interruption.

## Stop-work rule

Any mismatch, missing or ambiguous evidence, interrupted run, unexpected code/runtime/dependency change, failed attestation, unverified reviewer/key, or uncertain replay/rollback state means **NO-GO**. Stop and preserve the attempt and logs as nonofficial evidence. Do not silently repair the artifact, rerun with the same fixed seed ledger, resume, combine partial outputs, or allocate replacement seeds. Any new seed allocation requires a prospective amendment, independent review and new approval before execution. Only a new explicit user authorization can authorize a later run after all gates are independently re-evaluated.
