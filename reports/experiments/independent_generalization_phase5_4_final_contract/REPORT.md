# Phase 5.4 — Final Reduced Benchmark Contract

## Decision

# GO for a later, separately authorized reduced simulator benchmark

A defensible custom-simulator study can proceed without production-code changes under the narrowed objective and explicit evidence contract below. This GO does **not** authorize a run now. It does not cover physical backends, unknown-cause/evidence-withheld diagnosis, or coupling-edge localization. The run must use this contract, preserve the frozen family split, and receive separate execution authorization.

## Final objective and exclusions

Evaluate family-held-out diagnosis on five four-qubit circuit families using the existing custom simulator and diagnosis API. Measure output-distribution anomaly detection, normal/program/hardware classification, program-operation localization, supported qubit and calibrated gate-tuple localization, and abstention on a known combined-fault case. Labels are constructed from a predeclared intervention ledger, independent of predictions. Exact ideal references are derived analytically as documented in Phase 5.3; finite-shot observations remain sampled data.

Explicitly exclude:

- U1 evidence-withheld and U2 competing-cause observational-equivalence cases (`EXCLUDED_PENDING_DEFINITION`). Unknown-cause and evidence-withheld performance are outside this reduced benchmark's claims.
- C15 as a substitute for unknown-cause evaluation. C15 evaluates only a known simultaneous program+hardware intervention and its expected combined/ambiguous single-label result.
- Coupling-edge localization. The frozen ledger has no edge calibration evidence or physical/logical mapping, so this metric is deferred. Keep it separate from qubit and gate-tuple localization.
- Claims about physical/backend calibration accuracy, physical qubit mapping, or deployment performance. The calibration values are generated by and used inside the custom simulator.
- Output-anomaly positives for F3 masked SWAP P1/P2 and F5 T→Tdg P2. They remain program-fault classification cases because the expected/observed circuit difference is an allowed input; matching class success is never counted as output-anomaly detection success.

## Calibration and inference-time evidence contract

The ordinary `run_experiment` constructs two hardware models from the same `hardware_parameters`: one applies simulation noise and one is passed to diagnosis. `diagnose_execution` receives expected/observed distributions, expected/observed circuits, `hardware_model`, `threshold`, and `shots`. It receives normalized distributions, not raw counts. This is therefore an explicit **simulator-known-calibration** protocol: calibration values are visible because the local runner supplies them, and can reveal the injected mechanism/strength. They are not independent measurements and must not be described as such.

### Complete baseline profile (required for every retained simulator case)

To prevent defaults from masquerading as missing calibration, the frozen case builder must explicitly provide:

- Qubits q0–q3: `readout_error=0.0`, `t1=1e6`, `t2=1e6`, `status="available"`, `available=true` for each qubit.
- Every canonical gate and exact ordered operand tuple appearing in either expected or observed circuit: an explicit calibration entry with `error=0.0`, `duration=0.0`, `supported=true` unless a named fault override below applies. Include both sides of a program substitution so `_calibration_gaps` does not invent a missing gate calibration.
- `coupling_map=[]` and `edges=[]`. This explicitly means no edge-calibration evidence is supplied; it must not be interpreted as a healthy/ideal physical topology. Missing-edge evidence can be reported by the API, and no coupling-localization claim is made.
- No unspecified hardware property may be filled by relying on `HardwareModel` constructor defaults. A missing required field fails the design/config preflight; it is not silently converted to zero error or ideal calibration.

Scenario-specific overrides are limited to the declared readout p on the target qubit for R cases, declared gate skip probability p on the target canonical gate/tuple for G cases, and readout p=.15 plus the P1 circuit mutation for C15. All non-target fields retain the explicit baseline above. These calibration fields are the only hardware evidence admitted for those synthetic cases.

### If calibration is unavailable

For an external backend adapter, pass `hardware_model=None` when there is no independently supplied calibration record. Do not construct an ideal profile as a substitute. With distributions still available, output anomaly detection remains eligible. A visible expected/observed circuit pair still permits program mismatch classification/localization. A hardware-only cause cannot be positively localized or assigned a supported hardware class from absent calibration; the permitted cause result is the API's merged `AMBIGUOUS / INSUFFICIENT_EVIDENCE` category, and hardware localization is ineligible. Under the current runner, setting `hardware_parameters=None` also removes simulator hardware injection, so a simulated fault with hidden calibration cannot be represented as an ordinary retained run without changing the runner; such a case stays excluded.

### Custom simulator versus external backend

| Field/evidence | Custom simulator case | External backend adapter |
|---|---|---|
| Expected circuit/reference | Frozen circuit and analytically derived ideal distribution | Must be supplied from the intended source program and an independently computed reference |
| Observed circuit | Runner's configured submitted circuit, visible to diagnosis | Available only if backend/job record exposes the actually submitted/transpiled circuit; otherwise omit it and do not claim program-fault localization |
| Observed measurement | Simulator sampled counts normalized to `observed_distribution`, with shot count | Backend counts/probabilities and actual shots from job result |
| Calibration | Explicit synthetic profile also used to inject simulator noise; privileged, correlated evidence | Only adapter-provided calibration with source/time/units and mapping provenance; absent means `hardware_model=None` |
| Mapping/topology | Logical indices only; no edge map/calibration supplied in this benchmark | Requires adapter-provided mapping/topology; not present in the current experiment contract |
| Permitted claims | Local behavior under supplied synthetic evidence | None in this benchmark; external generalization is out of scope |

### Final model-input schema

Allowed: `expected_distribution`; `observed_distribution`; `shots`; `expected_circuit` and `observed_circuit` only under the explicit custom-runner or validated backend-job contract above; and only calibration fields present in the scenario's inference-visible `hardware_model`: per-qubit readout/T1/T2/status/availability, gate or edge error/duration/support and target tuples. Missing calibration remains missing. Features must be deterministic transformations of those fields and be frozen before evaluation.

Forbidden: case ID, family ID/name, split, scenario description, ground-truth label/cause, intervention name/type/target, explicit injected strength field, affected-target annotation, expected-detection flag, pair ID, seed, file path, result/evidence artifact, and label-derived encodings. Seeds and IDs remain only in the grouped audit ledger. The numeric calibration value itself is allowed only because this custom-simulator protocol explicitly supplies that value to diagnosis; disclose this direct evidence channel in every result summary.

## Final per-case scoring ledger

The retained case IDs are `{family_id}-{suffix}`. Suffixes are N0, P1, P2, R02/R06/R15/R30, G02/G06/G15/G30, and C15. Each row is instantiated in each of F1–F5. Each has five seeds (20263001–20263005) and shot counts 256, 1024, and 4096.

`D+`/`D−` means the exact intervention output distribution differs/does not differ from the ideal reference. It is independent from a finite-shot threshold crossing.

| Cases | Output-anomaly detection | Program vs hardware classification | Localization | Abstention |
|---|---|---|---|---|
| All `N0` | Negative controls | NORMAL | None | No |
| `P1/P2` in F1, F2, F4 | Positive anomaly cases (D+) | PROGRAM_FAULT | Program operation index/target | No |
| `P1/P2` in F3 | Negative output-anomaly controls (D−) | PROGRAM_FAULT via visible circuit mismatch | Signature/index only; not output-causal | No |
| F5 `P1` | D+ | PROGRAM_FAULT | Program operation index | No |

Localization claims are limited to target types the configuration actually supplies. Readout cases support qubit localization under the existing cutoff. Gate cases support gate-tuple localization under the supplied calibration. The current ledger contains no coupling edge entry, so coupling localization is not scored.

## Metrics, criteria, and threshold policy

Keep metrics separate; report confusion matrices with `NORMAL`, `PROGRAM_FAULT`, `HARDWARE_ANOMALY`, `COMBINED/AMBIGUOUS`, and insufficient-evidence/abstention dispositions. Never merge program classification correctness with output-detection correctness.

| Metric | Reporting | Reduced-scope acceptance target |
|---|---|---|
| Output anomaly | Sensitivity, specificity, balanced accuracy; exact D truth vs sampled decision; stratify by family, fault strength, and shots | Sensitivity ≥0.80 on identifiable moderate/severe D+ cases; specificity ≥0.90 on N0 and masked D− controls. Subtle p=.02 and below-threshold cases are reported descriptively, not pass/fail |
| Program/hardware/normal class | Per-class precision/recall/F1, macro-F1, confusion matrix; calibration-visible hardware cases called out | Macro-F1 ≥0.75 on identifiable single-cause classes; program-only and supported hardware-only recall ≥0.80. p=.02 is a separate descriptive stratum because hardware evidence does not cross the localizer cutoff |
| Combined cause | Multi-label target recovery plus categorical result | No single-cause prediction counts as correct combined diagnosis; report C15 support and results separately |
| Program/qubit/gate localization | Exact target accuracy and target precision/recall; report supported denominator and per-family counts | ≥0.70 exact target accuracy for supported, identifiable cases. Exclude p=.02, masked output localization, and coupling localization |
| Abstention | Coverage, selective risk, C15 AMBIGUOUS recall, incorrect confident single-cause rate | C15 ambiguous recall ≥0.80 and report coverage. No unknown-cause/evidence-withheld acceptance claim is made |
| Reproducibility | Per-seed scores, mean/SD/range, paired-control differences, config/reference hashes | Same frozen inputs and seed must reproduce identical artifacts; primary moderate/severe metric seed SD ≤0.10 where denominator permits |

The primary statistical threshold remains **0.05**. The implementation also applies a finite-shot guard `max(0.05,1/sqrt(shots))` (0.0625 at 256 shots; 0.05 at 1024/4096). Do not tune either value. The locked test is never used to select thresholds. F3 may be used only to fit a probability calibration map, not to choose a detection threshold. If the fixed thresholds fail the targets, report the failure; do not retune this benchmark.

## Case, configuration, and shot-execution counts

Fourteen templates were defined per family. U1/U2 are excluded, leaving 12 retained templates × five families = **60 cases**. Five seeds × three shot levels gives **900 configurations**. The runner performs one ideal and one observed shot pass per configuration. Total shot-circuit executions are:

`60 cases × 5 seeds × 2 passes × (256+1024+4096) = 3,225,600`.

This excludes ideal statevector/reference and diagnosis trace work. The prior estimate of about 9.6 MB for 900 JSON files is an extrapolation from Phase 2's ~10.7 KB mean case artifact; no Phase 5 runtime or storage benchmark was performed. Runtime remains unquantified.

## Final limitations and execution authorization

The reduced protocol is GO only for custom-simulator cases with the explicit profile contract, source-visible circuit inputs, family split, fixed threshold, exclusions, and score eligibility above. It cannot support unknown-cause abstention, coupling-edge localization, or external-backend performance. Calibration features are shared with simulator injection and therefore provide privileged simulated evidence. The 0.02 strengths are retained for detection/classification description but cannot be localized with the existing >0.05 evidence rules. F3/F5 masked program cases are not output anomalies. CCX hardware localization is restricted to the fully calibrated three-qubit target tuple.

No run is performed by this report. A later run requires a separate explicit authorization and must first verify that each case configuration supplies the complete explicit calibration profile described above; absent calibration must remain `None` and must not be replaced by ideal defaults.
