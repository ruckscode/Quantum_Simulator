# Finite-shot null-confirmation implementation-readiness review

**Review type:** implementation readiness only. The proposal is directionally useful, but it is not yet implementation-ready as written. In particular, a service does not prevent the legacy helper from being imported by another Python process, and the run-recovery language must be reconciled with the fixed seed ledger. No code or experiment artifacts were changed; no tests or sampling were run.

## Approval and trust verification requirements

The service or fixed task must not accept caller-provided expected hashes or an alternate trust path. The launcher should load its trust anchor from an administrator-controlled machine trust location (for example, a protected LocalMachine certificate/public-key store or protected configuration directory), compare the approval's key ID to that independently provisioned pin, verify the Ed25519 signature over the canonical approval payload, then compare the signed bundle digest, experiment ID, fixed preregistration/configuration digest, seed-ledger digest, and unique run ID to the staged worker manifest. The public key is not secret, but its identity mapping must be protected from the execution identity; the corresponding private key remains with the independent reviewer.

The approval itself may be presented as an untrusted input because any alteration must fail signature verification. The trust key/pin and the code that chooses it must not be supplied by the same requestor. The host must protect the trust store, launcher/task definition, worker image, every parent directory, and run ledger with administrator-controlled ACLs. The currently reported `C:\ProgramData\QuantumSimulator\finite-shot-null-confirmation` path is absent; there is no effective ACL evidence. Do not provision a production key or treat the current local binding record as authorization.

## Interrupted runs, seed reuse, and recovery

The existing fail-on-resume rule is scientifically conservative: consume the approval before any random draw and do not resume after a crash. The existing 38,228-pair seed ledger is deterministic and fixed by the preregistration. Reissuing an approval for the same ledger repeats the same random streams; it is reproducible rerunning, not an independent confirmation. The proposal's phrase “new reviewer-approved run and explicitly non-overlapping seed allocation” is therefore not implementable under the current fixed seed ledger without a prospective design change.

The deployment ledger should commit a run ID as consumed in a durable transaction before worker start and reject it on all later starts. Store state outside requestor control and protect against restoring an older snapshot. If the host cannot establish anti-rollback behavior, any reboot/restore ambiguity is a no-go. For this one run, simplest policy: a consumed or interrupted run is permanently abandoned; no automatic resume or rerun. Any future run with new seeds requires a new preregistration, independently reviewed approval, and explicit seed-protocol rationale.

## Smallest defensible implementation sequence

1. **Resolve scope and source lineage.** Define the protected claim as “the official registered confirmation result can only be produced by the authorized worker.” State that the legacy helper is not disabled in the general development checkout. If policy requires preventing every local call with those arguments, isolate execution on a host/image where the checkout and generic runner are absent and restrict Python execution; do not alter the pinned legacy source as a shortcut.
2. **Freeze a worker bundle.** Make a new versioned bundle from the unchanged registered statistical logic and fixed configuration. Enumerate/hash the worker, preregistration, detector, all transitive Python modules, Python runtime, standard library, NumPy and native extensions, cryptography and native dependencies, and DLL search paths. A lockfile and full manifest are required; a version string or `pyproject.toml` digest is insufficient. Keep statistical functions separately testable with analytical fixtures; only the official sampler/run orchestration is callable from the protected process.
3. **Select one fixed OS launcher.** For the single bounded run, implement a fixed Task Scheduler action under a dedicated non-interactive identity if administrators can lock task definition and arguments and restrict Run/Modify/Read rights appropriately. The caller can submit an approval/request but cannot choose a command, path, module, parameters or output destination. Use a service only if equivalent task isolation cannot be demonstrated or repeated operations will be required.
4. **Provision trust and durable state.** Administrator installs the reviewer public-key pin and fixed bundle manifest under protected ACLs; reviewer signs the exact final manifest and unique run ID. Create a durable, protected single-use run ledger and a separate write-limited output location. Verify owner, inheritance, effective rights, group membership, reparse protection, service/task configuration, backup/rollback and audit settings as the actual execution identity.
5. **Implement authorization before import/sample.** A small protected launcher verifies the signature and manifest before launching/importing the worker. It starts from a clean working directory and controlled runtime, ignores user-site/startup/import-path configuration, constrains Python and DLL imports to the protected bundle, and does not mount the development checkout. Consume the run transactionally before sampling. If authorization, hash, identity, runtime or ledger checks fail, exit before RNG.
6. **Adversarial acceptance without confirmation draws.** See the concrete tests below. Add unit tests using a spy RNG and test-only keys; then perform a separate deployment qualification with the actual service/task identity and administrator evidence. Do not launch the 38,228-pair run as part of implementation readiness.

## Concrete acceptance tests

All denial tests must instrument the sampler/RNG and assert zero calls. Test private fixtures only; do not create production keys or invoke the registered workload.

1. **Unauthorized entry points:** from the ordinary operator identity, try the legacy helper import/call, legacy runner CLI, direct confirmation-driver call, worker module import, worker executable, and every IPC/task interface. The official worker and its protected bundle must be inaccessible/executable only through the fixed launcher. Document explicitly that an ordinary local caller may still compute arbitrary samples if the legacy checkout remains available; the deployment must not accept such output as the official result.
2. **No helper callback bypass:** the service/task interface accepts only a fixed request schema and never exposes a generic “sample”, Python expression, module name, file path or arbitrary helper callback. A crafted request attempting each field fails before worker start or RNG. Inject a test sampler inside the worker to prove authorization runs first.
3. **Approval trust:** missing/wrong trust pin, changed key file, wrong key ID, malformed/duplicate JSON, altered signature, pending decision, wrong experiment ID, stale bundle digest, wrong run ID, or unapproved runtime all fail closed. Test keys remain isolated from production provisioning.
4. **Bundle substitution/import:** alter each source and binary dependency after approval; swap a path/junction during preflight; inject hostile `cwd`, `PYTHONPATH`, user site, `.pth`, `sitecustomize`, package shadow and DLL; change task/service action or arguments. Each must be denied before worker import or RNG. Repeat mutation attempts as the actual worker identity and show OS access denial throughout verification and execution.
5. **Replay/recovery:** concurrently trigger the same run twice; stop the process before sampling, mid-run under a test spy, and after consumption; restart the host/service/task; replay the same approval; restore a pre-consumption backup. At most one launch may consume the run ID; every interrupted/consumed ID fails after restart. If rollback cannot be detected or prevented, fail deployment qualification.
6. **Scientific invariance:** compare the new worker's pure detector, seed function, pair construction and endpoint calculations against the registered source with analytical fixtures and hashes. Validate 38,228 pairs, 1,024 shots, distributions, threshold and 2,217 cutoff without drawing confirmation samples. Any required change to seed allocation needs a new prospective preregistration.
7. **Real-host identity/ACL test:** as the actual service/task token, attempt to create, edit, replace, rename, delete, change ACLs on, or reparse every trust, bundle, launcher, runtime and parent path. Confirm only the intended run-ledger/output writes are allowed. Review effective rights including inherited and group grants. This cannot be substituted by a temp-directory pytest on the development identity.

## Go/no-go criterion

**Current decision: NO-GO for implementation deployment, provisioning, and experiment execution.** Readiness can advance only when all items below have evidence:

- Threat scope states whether “no unauthorized sampling” means no unauthorized official run or no call to any copy of the helper. The latter cannot be guaranteed while users retain the current readable checkout and general-purpose Python; the deployment must remove that access or narrow the claim.
- A fixed service or scheduled-task launcher prevents users from invoking the worker or running arbitrary code under its identity. Direct helper and alternate entry-point tests demonstrate that only the authorized operation can produce the official artifact.
- A complete immutable bundle covers all executable and imported code/dependencies; a changed bundle cannot execute with an earlier approval, and OS rights prevent replacement between verification and use.
- An independently authenticated reviewer key is pinned outside execution control, approval binds the exact bundle and run ID, and a durable protected ledger rejects replay after concurrent starts, interruption, restart and rollback.
- An administrator provides actual-host ACL, identity, service/task and trust-store evidence; adversarial tests pass under those identities without confirmation samples.
- The existing scientific registration remains unchanged. Any new seed allocation or restart policy is prospectively registered and independently reviewed.

Failure or missing evidence on any item is no-go. A passing proposal review is not approval to provision trust or execute the confirmation.
