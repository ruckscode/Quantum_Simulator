# Finite-shot null-confirmation control implementation plan

**Status: NO-GO.** This is a planning artifact only. No Windows task, identity, ACL, trust key, or execution was provisioned. The recommended target is a fixed, administrator-controlled one-shot scheduled task, conditional on proving that it enforces the same boundary as a protected service for the narrowly defined official result.

## 1. Security claim and official-result contract

The security claim is limited to the **official confirmation result**: only a complete run through the fixed protected worker may produce an artifact accepted as the registered confirmation. A user who retains the development checkout can still call or reimplement the legacy sampler. Such output is not an official result and must not be accepted or pooled as one. The operating system cannot stop arbitrary users from reproducing public mathematics on their own machines; it can protect the authorized execution identity, designated worker and official evidence channel.

An official result consists of a result payload plus a detached host execution attestation. A verifier must validate all of the following bindings:

| Binding | Required value/evidence |
|---|---|
| Experiment | Fixed experiment ID `finite_shot_null_confirmation_20261016`. |
| Registration | Exact preregistration bytes and digest; current driver-binding record lists SHA-256 `bd50e03c195b0b58c589364a2872eb17ab21e68534ee54d8e249917b59da8e20`. Recompute and recheck at staging. |
| Worker/runtime | Unique immutable bundle ID and complete signed manifest digest covering worker, detector/statistical helpers, interpreter/runtime, standard library, all Python/native dependencies and DLLs actually loaded. |
| Reviewer approval | Digest of canonical signed approval, trusted reviewer key ID, independent reviewer identity record, approval decision and review scope. Approval binds the bundle, experiment, registration, configuration, seed ledger, resource limits and run ID. |
| Run/replay state | Canonical unique run ID consumed exactly once by the protected durable ledger before any RNG call; run state records `consumed`, `complete`, or `aborted` and cannot be rolled back by the requestor. |
| Seed allocation | Exact registered seed protocol and ledger digest, including 76,456 unique streams and zero overlap; result records the allocation identity and digest. |
| Execution outcome | Completion state, 38,228 actual pairs, 1,024 shots, flags, resource accounting and endpoint. Partial runs are explicitly nonofficial. |
| Host attestation | Signature over the canonical result digest and all bindings above, created only after successful completion using a protected host key unavailable to requestors. Its public key is separately pinned for verification. |

A JSON result, `create-only` output, task history entry, or successful exit code alone proves none of these bindings. The current driver writes an unsigned JSON result (`experiments/finite_shot_null_confirmation.py:523–543`) under the repository reports tree (`:40`). It has no host execution attestation. Add a signed sidecar and protected completion ledger; the preregistered statistical endpoint remains unchanged.

The host attestation is distinct from the reviewer signature: the reviewer approves what may run; the host attests which protected run completed and what exact bytes it produced. Neither signature alone proves the other's claim.

## 3. Smallest defensible implementation sequence: one-shot scheduled task

The experiment is one bounded run, so a persistent service is unnecessary if Task Scheduler can provide the same OS boundary. Do not add a service preemptively. If the task's effective permissions, identity, fixed-action behavior or auditability cannot meet a listed acceptance criterion, stop and use a separately reviewed service design; do not weaken criteria.

1. **Freeze the claim and contract.** Define “official result” as a complete result plus valid host attestation, with matching reviewer approval, immutable bundle, fixed registration and consumed run ID. Explicitly exclude output from direct legacy helper calls. Freeze a canonical envelope/sidecar schema. Acceptance: an independent verifier can reject a forged JSON file without consulting its filename or process exit status.
2. **Inventory and freeze the worker bundle.** Keep the existing scientific functions and registration unchanged. Inventory exact source and runtime dependency closure, lock every artifact hash, derive a stable bundle ID, and prove local manifest validation/mutation detection with test fixtures. Acceptance: changes to any source, wheel/native extension, Python runtime component, configuration or seed ledger invalidate the manifest/approval.
3. **Implement protected bootstrap/task contract.** Build the smallest fixed launcher that accepts no caller-selected code, arguments, paths, configuration or output location. It verifies approval against a separately pinned key and verifies the complete bundle before import; it constrains import and DLL resolution to the bundle, then consumes the run ID before worker/RNG. Acceptance: all negative local tests below reject before RNG; integration confirms task action is fixed.
4. **Implement durable single-use state and terminal failures.** Use transactional consumption, concurrency exclusion and durable commit. A consumed run becomes `running`; successful full completion becomes `complete`; any interruption/exception becomes terminal `aborted` (or remains `running` but is treated as terminal). No resume from checkpoints. Acceptance: restart/replay/concurrent invocation cannot start the same run twice, and partial output cannot be attested.
5. **Implement result attestation.** Only the completed worker path may request host attestation, binding result bytes to the approval, bundle and ledger. Keep result and sidecar in a protected/controlled destination and provide a verifier. Acceptance: file edits, fabricated sidecars and signatures from untrusted keys fail; valid test fixtures round-trip.
6. **Add local adversarial tests and code-path inventory.** Use fake keys, fixture bundles, mocked task/ledger adapters and a spy RNG. Do not generate registered samples. Acceptance: test matrix below is green; static review finds no worker helper/RPC/CLI bypass inside the protected bundle; all denial paths report zero RNG/multinomial calls.
7. **Administrator deployment qualification.** Provision the actual Windows identity, task, trust root, immutable bundle, state store and host attestation key. Test ACLs and task/service controls using actual operator and task tokens, including inherited/group rights and reparse attempts. Acceptance: retained administrator evidence demonstrates effective denial; task cannot be altered or used as an arbitrary-code launcher; durable state survives restart and resists rollback.
8. **Independent review and separate execution decision.** External reviewer authenticates the final manifest and signs the unique run ID. Recompute binding after all code/deployment changes. Acceptance: reviewer identity/key evidence and valid approval match exactly; then request a separate execution authorization. This implementation plan itself is not that authorization.

## 4. Interruption and replay semantics

- **Resume same authorized run:** prohibited. Consume the run ID transactionally and durably before the first RNG operation. After a crash, process restart, host restart or uncertain ledger state, fail closed. Do not continue a checkpoint or resubmit the same run ID.
- **Restart from the beginning with the current seed ledger:** not an independent rerun. `stream_seed()` deterministically derives each stream from protocol, shot count, condition, replicate and role (`experiments/finite_shot_synthetic_characterization.py:45–55`). Reusing the fixed ledger reproduces the same streams; a different run ID does not make those observations independent. The current preregistration's 76,456 stream ledger is fixed and cannot be silently replaced.
- **New independent run with new seed allocation:** prohibited under the current preregistration. It needs a prospective amendment/new preregistration specifying seed derivation, uniqueness/collision and prior-overlap checks, full ledger digest, sample size, analysis and decision policy. It must be independently reviewed and signed before data generation. The detector/threshold/acceptance criteria may not be retroactively loosened.
- **Partial or failed run:** record terminal `aborted` state and any available non-sensitive execution metadata in the protected audit ledger; mark output partial and nonofficial. Do not publish a completion attestation, combine partial counts with a rerun, or represent a partial draw count as 38,228. A new allocation requires the prospective process above.

## 5. Threat-based negative-test matrix

Every rejection test instruments worker start and RNG entry; expected worker starts/draws are zero. “Local simulation” does not prove Windows ACLs or identity isolation.

| Threat | Test and expected result | Test boundary |
|---|---|---|
| Tampered approval/signature | Change any signed field/signature bytes; verifier rejects before task worker starts. | Local with test key; production key provisioning external. |
| Untrusted signing key | Sign with unrelated test key or substitute trust pin; key ID/signature mismatch rejects. | Local crypto simulation; actual key-to-reviewer authentication external. |
| Duplicate-key approval JSON | Include duplicate schema/decision/key/run fields; strict parser rejects before interpreting approval. | Local unit test. |
| Modified worker/dependency/runtime | Alter each manifest-listed source, package, native extension, interpreter component, config or ledger after approval; digest mismatch stops before import/RNG. | Local fixture-bundle test; ACL resistance requires actual task identity. |
| Import/DLL substitution | Hostile cwd, environment, user-site, `.pth`, startup hook, package shadow, alternate import path and DLL are present; none is loaded and startup rejects or records only pinned bundle paths. | Local process simulation; actual paths/ACL/runtime require deployment verification. |
| Verification-to-use swap | Attempt rename/reparse/replace between verification and import/use; worker either uses the same protected immutable version or rejects before RNG. | Race harness locally; effective prevention requires actual ACLs and task token. |
| Replayed run ID | Run ID already consumed; second launch rejects before worker/RNG, including concurrent starts. | Local transactional-store simulation; real atomicity/concurrency and persistence require target store. |

## 6. Explicit GO/NO-GO criteria

**Current decision: NO-GO.** Unit tests can validate parsing, signatures against fixture keys, manifests, state-machine rules and fail-before-RNG behavior. They cannot prove effective ACLs, task identity isolation, administrator ownership, actual reviewer independence, private-key handling, durable anti-rollback, or host-key restrictions.

Change to **GO for a separate execution-authorization review** only when all conditions have retained evidence:

1. The claim is limited to official result production; legacy helper calls in the developer checkout are expressly classified as untrusted and their artifacts cannot pass the official-result verifier.
2. The fixed scheduled task is admin-controlled, parameterless or accepts only a fixed authenticated approval input, and requestors cannot change/run arbitrary code as its dedicated noninteractive identity.
3. An administrator-provisioned reviewer key pin and host-attestation key are protected from requestor/task modification; reviewer identity/independence is independently verified.
4. A complete signed worker/runtime manifest covers all code and dependencies actually loaded; startup verifies before import; imports/DLLs resolve only to the immutable versioned bundle; attempts to alter or substitute files fail under the actual task identity.
5. A durable, atomic, protected run ledger consumes each run ID before RNG and rejects concurrent replay, interruption, restart and rollback. A consumed run is terminal; no retry uses the current seed ledger as independent data.
6. The official result sidecar verifies against the pinned host key and binds exact result bytes, experiment/preregistration, worker manifest, reviewer approval, unique run ID, seed allocation, complete 38,228-pair outcome and completion state.
7. Local negative tests pass with zero sample calls on rejection; separate administrator deployment tests prove effective ACL/identity/task protections. An independent reviewer signs the final manifest and unique run approval after those controls are reviewed.
8. Scientific settings remain exactly as registered: 38,228 pairs, 1,024 shots, fixed null distribution, detector/threshold, one-sided 5% Clopper–Pearson rule and 2,217-flag cutoff. No new seed allocation is used without prospective registration and review.

Any missing or failed item is **NO-GO**. Satisfying these criteria permits only a separate decision on whether to execute; this plan does not authorize execution.
